# First forward intent pair publication (C4)

C4 saves one fresh C3 Champion/Challenger pair at the explicit `intent_store_root / epoch_id` slot. The initial release supports only `MATCHED_BOOTSTRAP_UNTRADED_V1`: the matched bootstrap remained untraded before the opening anchor. It performs no settlement, return calculation, or continuing cycle advancement.

The domain APIs in `quantpits/research/forward_intent_publication.py` are:

- `prepare_first_forward_intent_publication`: the original 14 explicit C3 arguments plus keyword-only `intent_store_root`, `epoch_id`, `decision_deadline_utc`, `next_open_utc`, `market_timezone`, and `opening_policy`. Read-only READY returns a request digest for review.
- `publish_first_forward_intent_pair`: the same arguments plus `expected_request_digest`. A missing target requires fresh C3 preparation and exact request agreement. Source guards remain held through final verification.
- `inspect_first_forward_intent_pair(intent_store_root, epoch_id, *, expected_request_digest)`: offline inspection requiring no Production/provider/MLflow or inference. Verified `d1_inputs` contains two ordered `role / prior / intents / execution_assumption` entries using existing strict accounting types.

The public C3 API remains read-only and closes guards before returning. The private ownership transfer is for C4 only. Serialized PREPARED or READY summaries cannot authorize publication.

Run `python -B -m quantpits.scripts.publish_forward_intent --help`. Actions are `prepare`, `publish`, and `inspect`. Preparation/publication retain C3 flag names and add `--intent-store-root --epoch-id --decision-deadline-utc --next-open-utc --market-timezone --opening-policy`. Publication also requires `--expected-request-digest`. Inspection accepts only root, epoch, and expected digest. There is no caller-supplied clock or historical completion timestamp flag.

The root must already exist as a canonical absolute physical directory with mode 0700. The epoch directory is create-only; files use O_EXCL/0600, fsync, and canonical-path rereads. Changing the cycle under the same epoch does not create another slot. An existing request is adopted offline without live source preparation, overwrites, automatic repair, or cleanup.

The nine data members are `request.json`, `definitions.json`, `priors.json`, two `*_ranking.csv` files, `plans.json`, `anchor_prices.json`, `calendar_day.txt`, and `calendar_future.txt`. `manifest.json` and `completion.json` are separate records. Limits are 4 MiB per data member, 32 MiB total data, and 1 MiB per record. Both complete priors and the bootstrap manifest are retained; this does not claim retention of every original bootstrap file. Model/signal capsules remain references. Actual consumed calendars and price words/rows are retained locally.

The eight non-request logical members are inventoried first. A versioned canonical request body then determines the SHA256 request digest. The C4 request link in definitions is omitted from that logical inventory. The manifest inventories all nine final raw members; completion binds the raw manifest digest. This ordering has no digest self-reference. C4 serialization/reading/writing and CLI source have their own implementation identity. Physical root identity is checked during each I/O operation; new completions use the V2 content binding described below.

The reader checks exact inventory, canonical schemas, digests, role/source/date joins, full priors, rankings, plan/intent associations, and float32 word derivation into cash close and arm projections. It treats planner reports as retained reports, never reconstructs planner authority, and never reruns the production planner. Valid zero orders, signed cash, pending positions, and shortages remain valid.

`LOCAL_PREOPEN_OBSERVATION_V1` uses the local aware UTC clock and monotonic time. Cumulative disagreement must not exceed two seconds; the invocation budget is at most 600 seconds and each gate must be strictly before the decision deadline. The next-open date in the explicit timezone must match the next retained calendar session, and the deadline cannot exceed next-open. The operator confirms the actual exchange opening time. Neither clock nor exchange calendar is externally certified.

Completion records a data-bundle verification that occurred before its creation; it does not claim to prove its own future fsync. The final COMMITTED gate appears in the original safe JSON, which a formal run must preserve at a preauthorized location. Only that invocation's successful COMMITTED result grants local-observation prospective/epoch-start facts. Reader/adoption separately report `bundle_verified`, `completion_record_verified`, `recorded_time_claim`, and `d1_readable`; they never grant fresh prospective or epoch-start authority.

Exit codes: 0 for READY/COMMITTED/ADOPTED/VERIFIED; 2 for preconditions or request mismatch; 3 for VERSION_BREAK; 4 for CONFLICT; 5 for UNCERTAIN/INCOMPLETE. Post-write failures preserve actual or UNKNOWN write facts; process-control interrupts propagate. Missing completion cannot be backfilled. Complete bytes after a final timeout/uncertain gate cannot replace the original successful run record. Safe stdout excludes private epoch names, paths, securities, amounts, and raw exceptions.

Development tests use temporary workspaces. A real publication needs a concrete candidate, Production/Research/provider bindings, frozen selectors, a new cycle/deadline, request digest, one target, an approved safe-record location, and authorization with a maximum 600-second budget. Historical C3 preparation is not a future-cycle seal. Development acceptance and the first real run are recorded separately: after implementation and synthetic contract acceptance, downstream development can use this reader/schema without waiting for a market cycle. The first real publication must still pass its own time and source checks before claiming a forward epoch has started.

C4 propagates C3 component rejection reasons. The limited origin-tags maintenance path stores versioned `input_provenance.maintenance_admission` in the request and includes it in input/request digests; existing implementation provenance also binds the Research code executing the rule. Successful stdout retains its existing field set and empty `reason_codes`. Existing V1 requests need no optional maintenance material, and their bytes, digests and operations are not rewritten. C4/D1/D2/D3 readers validate the new protocol and exact identities. Inspect the request and corresponding surface observation for admission evidence; replaying safe JSON cannot grant publication authority.

Common missing-row inputs retain the full eligible inventory and per-arm coverage_counts. Partial input_provenance must carry coverage_policy=COMMON_ANCHOR_RANK_EQUAL_V1. The reader checks equal scored sets, missing_prediction reasons, ranking/plan counts, exact per-arm scored-union-holdings price sets, and their joint receipt. A COMPLETE role means its computation succeeded. Old complete records require no new field. Inspect/adopt still cannot create original publication success timing or a prospective_claim.


## Copying records and format compatibility

New `completion.schema_version=2` records use `FORWARD_RECORD_BINDING_V2`. Their `target_binding_digest` binds record kind, epoch, cycle/index, request digest and manifest digest. Continuing `store_bindings` use `FORWARD_CHAIN_STORE_V2`, binding the intent/settlement role, first request/manifest/operation, frozen selectors, definition request and schedule. Neither binding includes paths, device, inode, mtime or host identity. Request/bundle versions and the safe stdout schema are unchanged; request version 2 alone does not indicate portability.

Copy the four runtime stores and required original COMMITTED stdout bytes, restore directory mode 0700 and file mode 0600, and explicitly select the new roots. Reading, inspection and adoption neither rewrite records nor renew the original publication time or prospective claim. D1 consumes copied intents and original stdout; D3 reads copied chains; D2 continues from verified after-states without resetting bootstrap or epoch. Production, provider, definitions and models remain explicit inputs. This does not migrate an entire workspace or MLflow URIs.

V1 completions retain physical binding checks at their original location, with subsequent new records written as V2. A new V2 settlement can retain an unchanged V1 source completion and still be copied: its own verified content binding identifies the new settlement. The V1 intent itself remains bound to its original directory. Copied V1 records return `LEGACY_PHYSICAL_BINDING_MISMATCH`; no automatic conversion or rewriting occurs. Unknown, missing or ill-typed versions are rejected. Canonical-path, directory identity, file fingerprint, source mutation and create-only checks remain active during operations. Independent copies do not share a global lock; select one active copy after recovery. A code rollback must retain a V2 reader and must not downgrade published records. This format change does not change economic rules or introduce a production approval gate.
