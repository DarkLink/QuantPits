# Saving the first paper-account orders

The first order pair starts from the existing matched bootstrap and is saved at `intent_store_root / epoch_id`. The default `publication_mode=PAPER` supports creation whenever convenient, followed by settlement at the original scheduled trade date. Orders saved after opening carry AFTER_OPEN_SIMULATION. Neither an administrative deadline nor saved terminal stdout is required. Select the actual anchor and source capsules explicitly; do not substitute latest. See [continuation and HOLD](research_forward_continuation.md).

The domain APIs in `quantpits/research/forward_intent_publication.py` are:

- `prepare_first_forward_intent_publication`: the original fourteen explicit source arguments plus `intent_store_root`, `epoch_id`, `next_open_utc`, `market_timezone`, and `opening_policy`. `decision_deadline_utc=None` and `publication_mode="PAPER"` are optional. Read-only READY returns the request digest for review.
- `publish_first_forward_intent_pair`: the same arguments plus `expected_request_digest`. A missing target requires fresh C3 preparation and exact request agreement. Source guards remain held through final verification.
- `inspect_first_forward_intent_pair(intent_store_root, epoch_id, *, expected_request_digest)`: offline inspection requiring no Production/provider/MLflow or inference. Verified `d1_inputs` contains two ordered `role / prior / intents / execution_assumption` entries using existing strict accounting types.

The public C3 API remains read-only and closes guards before returning. The private ownership transfer is for C4 only. Serialized PREPARED or READY summaries cannot authorize publication.

Run `python -B -m quantpits.scripts.publish_forward_intent --help`. Actions: prepare, publish, inspect. Preparation/publication retain the preparation flags and require `--intent-store-root --epoch-id --next-open-utc --market-timezone --opening-policy`; publish also requires `--expected-request-digest`. `--decision-deadline-utc` is optional. Historical strict experiments may explicitly use `--publication-mode STRICT_PREOPEN`. Inspect accepts root, epoch and expected digest only. Historical creation timestamps cannot be supplied by callers.

The root must already exist as a canonical absolute physical directory with mode 0700. The epoch directory is create-only; files use O_EXCL/0600, fsync, and canonical-path rereads. Changing the cycle under the same epoch does not create another slot. An existing request is adopted offline without live source preparation, overwrites, automatic repair, or cleanup.

The nine data members are `request.json`, `definitions.json`, `priors.json`, two `*_ranking.csv` files, `plans.json`, `anchor_prices.json`, `calendar_day.txt`, and `calendar_future.txt`. `manifest.json` and `completion.json` are separate records. Limits are 4 MiB per data member, 32 MiB total data, and 1 MiB per record. Both complete priors and the bootstrap manifest are retained; this does not claim retention of every original bootstrap file. Model/signal capsules remain references. Actual consumed calendars and price words/rows are retained locally.

The eight non-request logical members are inventoried first. A versioned canonical request body then determines the SHA256 request digest. The C4 request link in definitions is omitted from that logical inventory. The manifest inventories all nine final raw members; completion binds the raw manifest digest. This ordering has no digest self-reference. C4 serialization/reading/writing and CLI source have their own implementation identity. Physical root identity is checked during each I/O operation; new completions use the V2 content binding described below.

The reader checks exact inventory, canonical schemas, digests, role/source/date joins, full priors, rankings, plan/intent associations, and float32 word derivation into cash close and arm projections. It treats planner reports as retained reports, never reconstructs planner authority, and never reruns the production planner. Valid zero orders, signed cash, pending positions, and shortages remain valid.

Default `PAPER_ACCOUNTING_TIME_V1` retains actual time observations. An optional deadline is an administrative fact, not an admission gate. Durations above the old 600 seconds, clock disagreement above two seconds, and clock adjustments are retained as observations/problem codes. Invalid wall times remain null. `accounting_time` describes preparation start, creation, data verification and BEFORE_OPEN / AFTER_OPEN_SIMULATION / UNKNOWN. Orders whose preparation crosses opening are labeled after-open. These facts grant no strict prospective proof. The explicit next-open date must still match the first calendar session after the selected anchor.

Completion retains `accounting_time_observations` through data verification before completion creation. Final publication observation remains in optional original stdout only. Paper COMMITTED, reader and adoption keep `prospective_claim=false` and the historical strict `epoch_started=false`; accounting availability comes from content verification. Legacy LOCAL_PREOPEN_OBSERVATION_V1 and explicitly selected STRICT_PREOPEN preserve their original deadline, 600-second, two-second and successful-output meanings.

Exit codes: success 0; preconditions/request mismatch 2; VERSION_BREAK 3; CONFLICT 4; UNCERTAIN/INCOMPLETE 5. Post-write failures report actual or unknown write facts; control interruptions propagate. Missing completion is not repaired. Complete persisted records can settle after current verification without proving that the original publisher returned final COMMITTED. Safe stdout normally excludes private paths, epoch, instruments, amounts and raw exceptions; explicit HOLD displays caller-supplied interval/reason.

Development uses temporary workspaces. Owners choose the real workspace, provider, account and write scope; documentation examples do not authorize production execution or model training. Paper operations require no administrative deadline or stdout file. Review dates, source identity, order counts and request digest before publication.

C3/C4/D2 treat arbitrary source differences or unavailable source-equivalence comparisons as observations. Paper accounting can continue when the other model, configuration, signal and account checks pass. Historical production code need not equal current research code. Current working files are still checked against the loaded source location, and their content fingerprint is recorded independently of HEAD. Corrupt signals, rebuilt-ranking contradictions, model/configuration changes and wrong predecessors still block accounting. The existing public decision-surface API retains its comparison semantics; the daily path grants neither strict same-segment equivalence nor maintenance admission.

New requests use `input_provenance.source_change`, with independent `schema_version=1` and `SOURCE_DIFFERENCE_OBSERVATION_ONLY_V1`. `production_comparison` records the two production source observations; `production_commit`/`production_digest` identify the current prediction source; `execution_commit`/`execution_tree`/`execution_implementation_digest`/`execution_code_digest` identify current research execution. `production_execution_comparison` is EQUAL, DIFFERENT or INCOMPARABLE, with an unavailability reason where applicable. These observations affect input/request digests, not account continuity. Legacy `maintenance_admission` records retain their existing reader contract. Portable completion V2 bindings are independent of this field version. Code rollback must retain a reader for new records; historical records are not rewritten. Paper timing and optional stdout follow the rules above; legacy strict records, duplicate-write checks and interruption contracts remain compatible.

Common missing-row inputs retain the full eligible inventory and per-arm coverage_counts. Partial input_provenance must carry coverage_policy=COMMON_ANCHOR_RANK_EQUAL_V1. The reader checks equal scored sets, missing_prediction reasons, ranking/plan counts, exact per-arm scored-union-holdings price sets, and their joint receipt. A COMPLETE role means its computation succeeded. Old complete records require no new field. Inspect/adopt still cannot create original publication success timing or a prospective_claim.


## Copying records and format compatibility

New `completion.schema_version=2` records use `FORWARD_RECORD_BINDING_V2`. Their `target_binding_digest` binds record kind, epoch, cycle/index, request digest and manifest digest. Continuing `store_bindings` use `FORWARD_CHAIN_STORE_V2`, binding the intent/settlement role, first request/manifest/operation, frozen selectors, definition request and schedule. Neither binding includes paths, device, inode, mtime or host identity. Request/bundle versions and the safe stdout schema are unchanged; request version 2 alone does not indicate portability.

Copy the four runtime stores and optionally preserve any original COMMITTED stdout bytes, restore directory mode 0700 and file mode 0600, and explicitly select the new roots. Reading, inspection and adoption neither rewrite records nor renew the original publication time or prospective claim. Settlement consumes complete copied intents with optional stdout; D3 reads copied chains; D2 continues from verified after-states without resetting bootstrap or epoch. Production, provider, definitions and models remain explicit inputs. This does not migrate an entire workspace or MLflow URIs.

V1 completions retain physical binding checks at their original location, with subsequent new records written as V2. A new V2 settlement can retain an unchanged V1 source completion and still be copied: its own verified content binding identifies the new settlement. The V1 intent itself remains bound to its original directory. Copied V1 records return `LEGACY_PHYSICAL_BINDING_MISMATCH`; no automatic conversion or rewriting occurs. Unknown, missing or ill-typed versions are rejected. Canonical-path, directory identity, file fingerprint, source mutation and create-only checks remain active during operations. Independent copies do not share a global lock; select one active copy after recovery. Rollback must retain readers for V2, PAPER_ACCOUNTING_TIME_V1, optional stdout and HOLD without downgrading published records. This format change does not change economic rules or introduce a production approval gate.
